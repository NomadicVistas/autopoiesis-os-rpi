# Backend Release Rollout Contract Gate

## Summary

Generate a read-only hosted release rollout contract bundle so Admin > Frames update controls can prove durable rollout state before broad device updates are enabled.

## Context

The device already validates release manifests before applying code and exports local `release_history` events through heartbeat. The hosted side still needs one staging/CI evidence bundle that ties together the release row, per-device rollout row, queued `update_device` command, admin audit authorization, and heartbeat-ingested release-history event.

## Proposed Bundle

Optional staging/CI adapter:

```txt
GET /api/admin/frames/release-rollout-contract-bundle
```

Root shape:

```json
{
  "ok": true,
  "kind": "autopoiesis_frames_release_rollout_contract",
  "schemaVersion": 1,
  "generatedAt": "2026-06-07T01:15:00.000Z",
  "releases": [],
  "rollouts": [],
  "commands": [],
  "adminAudits": [],
  "deviceEvents": []
}
```

## Required Evidence

- `releases`: durable `aos_software_releases` rows with stable id, semantic version, channel, status, optional tag/git metadata, and optional rollout percentage.
- `rollouts`: durable `aos_release_rollouts` rows with stable id, release id, device id, target version, status, command id when available, and progress/failure timestamps.
- `commands`: queued or completed `update_device` command rows referencing known release/rollout evidence and carrying `authorization.approved=true`, `action="update_device"`, accepted actor role, timestamp, and audit id.
- `adminAudits`: optional durable admin command audit rows for the same update action.
- `deviceEvents`: heartbeat-ingested `release_history` events from `aos_device_events`, keyed by `deviceId + eventKey`, referencing known release/rollout ids when present.

## Acceptance

```bash
AUTOPOIESIS_RELEASE_ROLLOUT_CONTRACT_TOKEN="$TOKEN" \
  scripts/release-rollout-contract-check.sh "https://autopoiesis.art/api/admin/frames/release-rollout-contract-bundle"
```

The checker should pass only when update rollout progress is backed by durable release, rollout, command/audit, and device-event evidence. It rejects unknown references, duplicate ids/event keys, missing update authorization/audit ids, missing terminal rollout progress, artifact URLs/checksums, device credentials, tokens, secrets, and local appliance paths.

## Open Questions

- Should this bundle be generated by a staging-only admin adapter, seeded route integration tests, or the release promotion job itself?
- Which statuses should Admin > Frames display as terminal success, terminal failure, paused, or in-progress once `aos_release_rollouts` rows are populated?
- Should support-bundle uploads be allowed to backfill release-history rows, or should heartbeat ingestion remain the only source for rollout progress?
